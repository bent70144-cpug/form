# Glossary

Domain vocabulary as finalized in code: `packages/database/src/schema/index.ts`
and migrations `0002`–`0006` (plus `packages/form-schema` for the schema
envelope). Definitions match the implementation, not aspirations. See
`spec.md` for the full requirements; sections are referenced per entry.

## app_user

Postgres role used by the API for all request handling, via the pooled
`DATABASE_URL`. It has no `BYPASSRLS`; `SELECT`/`INSERT`/`UPDATE`/`DELETE` on
`workspaces` and `workspace_members` are revoked from it, so those tables are
reachable only through security-definer functions. See `spec.md`
["Tenancy and authorization"](spec.md#tenancy-and-authorization).

## audit_logs

App-schema tenant table recording one row per audited action (`action`,
`actor`, `target_type`/`target_id`, `metadata`, `ip_hash`), written in the same
transaction as the state change it records. Forced RLS; append-only —
non-owner roles get `INSERT` + `SELECT` and no `UPDATE`/`DELETE`. Created in
migration `0003_audit_outbox.sql`. See `spec.md`
["Data model"](spec.md#data-model).

## Block

One step in a form's sequence of blocks. The M0 union (`packages/form-schema`)
has four kinds; block IDs are 12-character URL-safe nanoids generated by the
client, validated server-side against `^[A-Za-z0-9_-]{10,32}$`, and unique
within a form. Only question blocks produce answers; the envelope is stable so
new kinds are added without changing it. See `spec.md`
["Form schema and versioning"](spec.md#form-schema-and-versioning).

- `welcome` — statement block shown first (optional, at most one, must be
  first when present).
- `short_text` — question block with a 1,000-character answer cap.
- `long_text` — question block with a 10,000-character answer cap.
- `ending` — closing statement block (optional, at most one, must be last
  when present).

## draft_version

Integer column on `form_drafts` that starts at 0 and increments on every
successful save. A save request whose supplied `draft_version` does not match
the stored value is rejected with 409 instead of overwriting another tab's
edit. See `spec.md`
["Form schema and versioning"](spec.md#form-schema-and-versioning).

## fn_owner

Dedicated `NOLOGIN` Postgres role that owns all security-definer functions
(migration `0006`). It has no `BYPASSRLS` — forced RLS binds table owners
too — so its access is exactly its explicit `TO fn_owner` policies, which
carry both `USING` and `WITH CHECK` and are separate from the `app_user`
tenant policies. It receives transient `CREATE` on schema `app` during
migration `0006` only; the privilege is revoked at the end of that file.

## form_drafts

One mutable row per form (`UNIQUE (workspace_id, form_id)`) holding the full
schema JSONB, the `draft_version` counter, and last-editor metadata. No
grants on this table are given to `fn_owner`, so security-definer functions
structurally cannot read drafts. Created in migration `0004_forms.sql`. See
`spec.md` ["Data model"](spec.md#data-model).

## form_sessions

Tenant table for public respondent sessions: hashed session token (unique),
pinned form version, expiry/completion timestamps, HMAC-derived `ip_hash`, and
user agent. A session is usable for 24 hours, submissions are accepted for a
5-minute grace window after expiry, and sessions expired for more than seven
days are deleted by the worker through `purge_expired_sessions()`. See
`spec.md` ["Public form and submission lifecycle"](spec.md#public-form-and-submission-lifecycle).

## form_slugs

Global registry mapping a public slug to a form, with an `is_current` flag and
globally unique slug. The only write path is the security-definer
`register_form_slug(form_id, slug)`, which verifies the form belongs to the
active workspace and rejects reserved route names; a superseded slug stays in
the registry and resolves as a `redirect` to the canonical slug. See
`spec.md` ["Form schema and versioning"](spec.md#form-schema-and-versioning).

## form_versions

Immutable published snapshots of a form's schema, numbered by a
`version_number` that is unique per form (`UNIQUE (form_id, version_number)`).
Publishing locks the form row and inserts the next version in the same
transaction as the pointer update, slug registration, audit row, and outbox
event; published rows are never edited. See `spec.md`
["Form schema and versioning"](spec.md#form-schema-and-versioning).

## forms

Tenant table representing a form in the dashboard: workspace, project,
`name` (dashboard label), `status` (`draft`, `published`, or `closed`), a
pointer to the current draft, and a pointer to the published version.
Respondents never see `forms.name` — they see the pinned schema's `title`.
Soft-deleted forms resolve to `closed` on the public API. See `spec.md`
["Data model"](spec.md#data-model).

## migrator

Postgres role that owns the `app`, `auth`, and `pgboss` schemas and all
tables; migrations run as this role over the direct (non-pooled)
`MIGRATOR_DATABASE_URL`. That URL exists only as a GitHub Actions secret and
never appears in Render's runtime environment. Created by the one-time admin
bootstrap (`pnpm db:bootstrap`).

## outbox_events

Transactional-outbox table and the one intentional non-tenant table: no
`workspace_id` column and no RLS — the workspace id travels inside the JSONB
payload (IDs, not PII). `app_user` gets `INSERT` only (no `SELECT`, so inserts
must not use `RETURNING`); `worker_user` gets `SELECT`/`UPDATE` for the
dispatcher, which claims batches with `FOR UPDATE SKIP LOCKED`, retries with
exponential backoff, and dead-letters after 10 attempts (ADR 0005). See
`spec.md` ["Queue, outbox, and audit"](spec.md#queue-outbox-and-audit).

## Pinned session

Property of a `form_sessions` row: it stores the `form_version_id` the
respondent started on, and submission validation runs against that pinned
schema even if the form is republished afterwards. If the form is unpublished,
closed, or deleted, submission is rejected even for a pinned session. See
`spec.md` ["Public form and submission lifecycle"](spec.md#public-form-and-submission-lifecycle).

## projects

Tenant table grouping forms inside a workspace; bootstrap creates one
`is_default` project named `General`, found by flag, never by name. Forms
reference their project through the composite foreign key
`(workspace_id, project_id)`. Created in migration `0002_workspaces.sql`. See
`spec.md` ["Data model"](spec.md#data-model).

## RLS

Row-level security: enabled **and forced** on every tenant table, so table
owners are subject to it too. Every policy carries both `USING` and
`WITH CHECK` against
`workspace_id = nullif(current_setting('app.workspace_id', true), '')::uuid`
(the `workspaces` root table compares `id` instead); `nullif` turns an unset
setting into NULL, so a query without tenant context returns no rows rather
than erroring. No runtime role has `BYPASSRLS`. See `spec.md`
["Tenancy and authorization"](spec.md#tenancy-and-authorization).

## schemaVersion envelope

The stable form-schema document stored in drafts and versions:
`{ schemaVersion: 1, title, blocks, logic, theme, settings }`. Future schema
changes go through explicit registered migration functions
(`migrateSchema` in `packages/form-schema`, where version 1 is the identity),
never in-place JSON edits. The empty draft is exactly
`{ schemaVersion: 1, title: "", blocks: [], logic: [], theme: { preset: "default" }, settings: {} }`.

## Security-definer function

SQL function that runs with its owner's privileges — here always the
`NOLOGIN` `fn_owner` role — as the only widened access beyond RLS. Each one
pins `SET search_path = app, pg_temp`, revokes `EXECUTE` from `PUBLIC`, and
grants it only to its caller role. The set (migration `0006`):
`list_workspaces()`, `create_personal_workspace()`, `get_published_form(slug)`,
`resolve_public_form(slug)`, `register_form_slug(form_id, slug)`,
`resolve_form_session(token_hash)` (all `app_user`), and
`purge_expired_sessions()` (`worker_user` only). See `spec.md`
["Tenancy and authorization"](spec.md#tenancy-and-authorization).

## submissions

Tenant table storing one answers JSONB object keyed by block ID (plus a
metadata JSONB) per `form_session_id` — unique, so at most one submission per
session; a retry returns a receipt without stored answers. Submission runs in
one transaction that re-validates answers against the pinned schema and
enforces the per-form cap (409 `form_full` at the default 1,000 in the alpha).
See `spec.md` ["Public form and submission lifecycle"](spec.md#public-form-and-submission-lifecycle).

## worker_user

Postgres role used by the worker over the direct (non-pooled)
`WORKER_DATABASE_URL`. It has `SELECT`/`UPDATE` on `outbox_events`, `EXECUTE`
on `purge_expired_sessions()` (its only cross-tenant access to
`form_sessions`), and no `BYPASSRLS`. See `spec.md`
["Tenancy and authorization"](spec.md#tenancy-and-authorization).

## workspaces

The tenancy root table, keyed by `id` (every other tenant table carries
`workspace_id NOT NULL` referencing it). `is_personal` plus a partial unique
index on `creator` guarantees at most one personal workspace per user, created
idempotently by `create_personal_workspace()`. Direct `SELECT` on this table
is revoked from `app_user`; it is reachable only via `list_workspaces()` /
`create_personal_workspace()`. See `spec.md`
["Tenancy and authorization"](spec.md#tenancy-and-authorization).

## workspace_members

Tenant table linking users to workspaces with a `role` from the
`owner`/`admin`/`editor`/`viewer` enum (unique per workspace/user). M0 creates
only the `owner` membership; the role model exists so collaboration needs no
migration later. Like `workspaces`, it has no direct grants to `app_user` and
is reachable only through the security-definer functions. See `spec.md`
["Data model"](spec.md#data-model).
